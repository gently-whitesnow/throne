# ADR-0004: MCP call audit log

## Status

Accepted (amended: добавлена секция §4 «Гарантия покрытия» — четырёхслойная защита от того, что новый MCP tool окажется без логирования; стало fitness function + startup fail-fast + параметризованный smoke-тест)

## Context

Центральная гипотеза `intent.md` §4: ценность MVP не в том, что система уже улучшается, а в том, что она **собирает правильный материал** для будущего обучения. На уровне домена этот материал уже фиксируется через коллекции `intent_qa`, `intent_review` и `text_versions` (см. [ADR-0002](0002-domain-model-and-text-versioning.md)). Но этих следов недостаточно, чтобы реконструировать рабочую сессию агента целиком:

- какие MCP tools агент звал и в каком порядке;
- какие `match_not_found` / `match_ambiguous` ошибки он получил, прежде чем правка применилась;
- сколько `read_*_text` агент сделал перед правкой (сигнал, что инструкции не дают агенту достаточно контекста);
- какие tools реально не используются (сигнал на сокращение API surface);
- сколько правок text прошло без сопряжённого `add_intent_qa` в interview-режиме (сигнал из [ADR-0003 §5](0003-mcp-text-editing-semantics.md), что инструкция interview не работает).

Без отдельного журнала этих сигналов либо нет, либо они размазаны по логам приложения и теряются. Это блокирует «улучшение системы — следующая итерация», ради которой MVP вообще пишется.

Рассмотренные альтернативы:

1. **Использовать только OpenTelemetry traces.** OTel удобен для performance-наблюдения, но дорого хранится длительно, схема каждого экспортёра своя, выгрузка в обучающий пайплайн потребует отдельной интеграции. Отклонено как первичное хранилище; OTel остаётся для performance/health (см. `USER.md`, Cross-cutting).
2. **Писать журнал внутри тех же документов `Intent` / `Instruction`.** Раздуло бы их, перемешало canonical state с трейсом. Отклонено.
3. **Журнал в Serilog file sinks + ротация.** Stdout-логов недостаточно для запросов «дай мне все tool-вызовы за конкретный intent_id за последние сутки» — нужен запросный store. Отклонено как первичное; Serilog продолжает писать общий лог приложения.
4. **Отдельная Mongo-коллекция `mcp_call_log` (выбрано).** Та же база, тот же транспорт, нативные запросы по `intent_id` / `session_id` / `tool_name` / `created_at`. Append-only, без миграций.

## Decision

### 1. Где живёт журнал

Отдельная Mongo-коллекция `mcp_call_log` в той же базе, что и `intents` / `instructions`. Append-only, удалений и обновлений нет (консистентно с `intent.md` §13: «в MVP ничего не удаляется и не архивируется»).

### 2. Структура записи

```text
McpCallLog
- id              : string
- created_at      : timestamp (UTC, сервер)
- session_id      : string?      // если MCP-транспорт прокидывает идентификатор клиентской сессии
- tool_name       : string       // напр. "replace_intent_text"
- arguments       : document     // raw JSON входных аргументов tool, как пришли от клиента
- intent_id       : string?      // вытаскивается из arguments если есть (intent_id в args)
- mode_hint       : string?      // если tool — get_instruction_bundle, сюда пишется mode; иначе null
- outcome         : enum { success | error }
- error_code      : string?      // для error: код из ErrorCodes (см. ADR-0003)
- result_summary  : document?    // для success: компактная выжимка ответа (новый current_version, total_lines, matches_count, и т.п.) — НЕ полный response
- duration_ms     : int
- server_version  : string       // semver приложения, чтобы потом отделять трассы разных версий поведения
```

Дизайн-правила для полей:

- `arguments` пишутся как есть. Solo-first MVP не имеет секретов в `Intent.text` или `Instruction.text` — те же данные уже хранятся в canonical-документах. PII-маскирование вернётся при появлении multi-user (см. Out of scope).
- `result_summary` — **не** полный response: для `read_*_text` и `search_*_text` это раздуло бы коллекцию суммарным размером ответов, а для дообучения нужен только сигнал «что сервер вернул на верхнем уровне». Полный текст исторической версии уже воспроизводим через replay цепочки delta из `text_versions` (см. ADR-0002 §4).
- Для `get_instruction_bundle` `result_summary` хранит логическую проекцию `InstructionBundleUse`: `mode`, опциональный `intent_id`, `instructions[]` как `{ kind, instruction_id, version }`, `missing_kinds[]`. Отдельная коллекция не нужна в MVP: факта в `mcp_call_log` достаточно, чтобы связать review/qa/outcome с версиями инструкций, активными в конкретной сессии.
- `error_code` берётся из единого реестра `Throne.Application.ErrorCodes`, того же, что использует Problem Details writer — без расхождения.

### 3. Где живёт логирующий код

Единый middleware на уровне `Throne.Api`, на границе MCP transport, **до** того как handler tool'а получает управление и **после** возврата результата (в т.ч. при exception). Никакой логики записи в `mcp_call_log` внутри `Throne.Application` или `Throne.Domain` — иначе Domain/Application знали бы о транспорте, что нарушает [ADR-0001](0001-foundation-clean-architecture-monorepo.md).

Запись в Mongo идёт через отдельный порт `IMcpCallLogSink` в `Throne.Application` с реализацией `MongoMcpCallLogSink` в `Throne.Infrastructure`. Middleware зовёт этот порт.

Запись журнала **никогда не должна ломать tool-вызов**: ошибка sink логируется в Serilog как warning и не пробрасывается клиенту. Это специально, потому что недоступность audit-log не должна делать сам MCP API недоступным.

### 4. Гарантия покрытия (coverage by construction)

Любой MCP tool по построению попадает в `mcp_call_log` — это инвариант, а не «не забыть добавить логирование при создании нового tool». Без этого ADR — пожелание, что нарушает `USER.md` («правило, не проверяемое билдом или CI, — не правило»).

Реализация:

1. **Единственная точка регистрации.** В `Throne.Api` есть helper-метод (условно `IEndpointRouteBuilder.MapMcpTool<TArgs, TResult>(name, handler)` или эквивалент через `IMcpServerBuilder`), который при регистрации **оборачивает** handler в audit-decorator. Прямая регистрация tool'а в `ModelContextProtocol` SDK мимо этого helper'а запрещена.
2. **Architecture-тест** в `Throne.Architecture.Tests` проверяет:
   - запрет на использование низкоуровневых API регистрации MCP tool'ов в `Throne.Api` напрямую (только через helper);
   - что все типы / методы, помеченные атрибутом MCP tool из SDK (`[McpServerTool]` или эквивалент), достижимы из единственного registration-helper'а.
3. **Startup fail-fast.** При старте `Throne.Api` после регистрации tools проверяется через `IServiceProvider`/`ToolRegistry`, что у каждого зарегистрированного tool'а в pipeline присутствует audit-decorator. Отсутствие — `InvalidOperationException` на старте, приложение не поднимается. Это страхует от случая, когда architecture-тест обманули новой обходной API SDK.
4. **Smoke integration-тест** в `Throne.Api.Tests`: вызвать каждый зарегистрированный tool через тестовый MCP-клиент и проверить, что в Testcontainers Mongo появилась соответствующая `mcp_call_log` запись. Тест параметризован по списку tools из реестра — добавление нового tool'а автоматически добавляет тест-кейс, забыть нельзя.

Слой 1 — устройство кода (helper); слой 2 — статическая проверка (architecture test); слой 3 — runtime-проверка (startup); слой 4 — поведенческая проверка (integration test). Любой слой ловит «забыли подключить логирование» — три из четырёх делают это до того, как код доедет до прода.

Никаких opt-in флагов «не логировать этот tool» не вводится. Если когда-то понадобится исключить tool из лога (например, чисто-readonly performance-чувствительный) — это будет отдельный ADR с явным списком исключений; сейчас политика — лог всегда.

### 5. Транзакционность

Запись `mcp_call_log` **не** в одной транзакции с доменной операцией. Tool-вызов сначала выполняется и фиксируется в основных коллекциях (`intents` + `text_versions`, либо `intent_qa` / `intent_review`), затем пишется audit-запись. Возможна редкая ситуация: операция применилась, журнальной записи нет (упал sink). Это допустимо для MVP — журнал работает на best-effort, а canonical state защищён `current_version` + version-документами.

Альтернатива «оба в одной транзакции» отвергнута: она сделает доступность журнала жёсткой зависимостью для каждой MCP-операции, что несоразмерно ценности audit-данных в MVP.

### 6. Индексы

Для поддержки целевых запросов:

- `{ intent_id: 1, created_at: 1 }` — выборка трассы по конкретному Intent.
- `{ session_id: 1, created_at: 1 }` — выборка трассы по клиентской сессии.
- `{ tool_name: 1, created_at: 1 }` — usage-метрики и выявление неиспользуемых tools.
- `{ created_at: 1 }` — по умолчанию для time-range запросов.

Все индексы создаются bootstrap-логикой при старте приложения, idempotent (как и для `intents` / `instructions`).

### 7. Чтение журнала

В MVP отдельных MCP tools для чтения `mcp_call_log` **не** добавляем. Журнал читается:

- напрямую через `mongosh` / любой Mongo client при ручном анализе dogfooding-сессий;
- любыми будущими ETL-скриптами, которые понадобятся для обучения системы.

Когда появится потребность отдавать журнал агенту (например, для самоанализа), это будет отдельный ADR с явным контрактом.

### 8. Связь с qa-телеметрией из ADR-0003

Метрика «доля text-правок без сопряжённого `add_intent_qa` в interview-режиме» вычисляется поверх `mcp_call_log` ad hoc-запросом: `replace_intent_text` / `insert_intent_text_after_line` для данного `session_id` без `add_intent_qa` в окне ±N секунд. Это первый практический потребитель журнала и обоснование, что схема (`session_id`, `tool_name`, `intent_id`, `created_at`) достаточна.

## Out of scope MVP

- PII-маскирование `arguments`. Включается, когда появляется multi-user или явные секреты в текстах.
- TTL / архивация старых записей. Принцип «ничего не удаляется» из `intent.md` §13 сохраняется. Если коллекция вырастет до проблемного размера, решение — отдельный ADR.
- MCP tools для чтения журнала.
- Структурированные events помимо tool-вызовов (например, «агент начал interview»). Если потребуются — отдельный ADR; сейчас все нужные сигналы выводимы из последовательности tool-вызовов.
- Экспорт в обучающий пайплайн.

## Consequences

### Positive

- Полная трасса agent ↔ MCP сохраняется в той же БД, без новой инфраструктуры.
- Запросы «что делал агент в этой сессии», «какие tools реально используются», «сколько `match_not_found` агент схватил, прежде чем применить правку» становятся прямыми Mongo-запросами.
- Best-effort sink + clean-architecture middleware изолируют журналирование от доменного кода и от доступности самого журнала.
- Совместимо с принципами `USER.md`: единый реестр кодов ошибок переиспользуется, OpenTelemetry остаётся отдельным каналом для performance/health.

### Negative / Risks

- Best-effort запись означает, что в редких случаях canonical-операция применится, а журнальной записи не будет. Принято осознанно: цена strong-consistency больше выгоды.
- `arguments` без маскирования — допустимо для solo-first MVP, но станет блокером в момент перехода на multi-user. Переход потребует миграции (back-fill маскирования или отказ от исторических записей).
- Коллекция растёт линейно с активностью агента. На горизонте dogfooding-объёмов это безопасно; на горизонте «продукт с многими пользователями» потребуется retention policy. Сигнал на отдельный ADR — не сейчас.
- Журнал — Mongo-only. Если когда-то storage сменится, журнал переезжает вместе со всей системой; абстракция `IMcpCallLogSink` это покрывает, но риск vendor-lock на Mongo в части аналитики выше, чем для основного state.
