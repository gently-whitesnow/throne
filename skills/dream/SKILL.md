# Throne Dream Operations

Цель — улучшить набор user-частей промпта (`scope=user`) на основе анализа реальных
диалогов. После ADR-0036 user-инструкция — это не пара {work, interview}, а множество
`prompt_part` с ролями по режимам: ядро (`common`, `work`, `interview`, `dream`) и
модульные/опциональные части (`dotnet`, `contracts`, `tests`, `commit`, `postgres`,
`mongo`, `frontend`, …). Думай структурой частей: не «какую строку дописать в work», а
«в какой части должно жить правило, не дублируется ли оно, не пора ли часть схлопнуть/
вынести/выпилить». Throne не хранит диалогов — читаешь их локально через Read/Glob по путям
из `sources`. См. ADR-0036 (PromptPart, роли, композиция), ADR-0038 (структурные патчи:
`create`/`set_roles`/`delete`), ADR-0022 (dream-flow).

У dream два режима, и оба — полноценный output:
- **Сигнальный** (default) — найти новые операторские сигналы в диалогах и пристроить в
  носитель. Плейбук ниже.
- **Структурный аудит** (standalone) — осмыслить НАБОР частей как граф и подрезать/
  реорганизовать его БЕЗ новых сигналов. Триггер: сигнальный проход не нашёл нового ИЛИ
  оператор явно просит аудит. См. раздел «Структурный аудит».

Output — не только «дописать буллет». Патч несёт `operation` (ADR-0038): `replace_text`
(default), `create` (новая часть + роли), `set_roles` (сменить роли — демоут/промоут),
`delete` (ретайр части). Удаление, демоут и расщепление части — такой же валидный итог
dream, как добавление правила.

Объём выбирает оператор — не подтягивай больше, чем явно попросили («посмотри 10» = 10).

## CLI (`skills/dream/bin/throne-dream`, читает `THRONE_API_BASE`)

```bash
skills/dream/bin/throne-dream sources                       # {vendor → path, hint} для локального чтения
skills/dream/bin/throne-dream parts                         # КАРТА частей: scope/key, version, роли по режимам
skills/dream/bin/throne-dream parts --json                  # сырьё: mode_roles целиком (нужно для set_roles/delete)
skills/dream/bin/throne-dream sessions --host "$(hostname)" --limit 5
skills/dream/bin/throne-dream current-part --scope user --key work
skills/dream/bin/throne-dream patches --status applied --limit 20
skills/dream/bin/throne-dream get-patch <id>
skills/dream/bin/throne-dream propose-patch  < /tmp/patch.json   # payload несёт operation (см. шаг 9)
skills/dream/bin/throne-dream record-session < /tmp/session.json
```

`propose-patch` принимает любую из четырёх операций (ADR-0038), не только `replace_text` —
матрица полей в шаге 9. Структурную правку (расщепить часть, демоут роли, ретайр) ты
формулируешь теми же патчами, а не словами в чат.

## Плейбук

1. **Карта частей — ГЕЙТ перед любыми патчами.** Строй карту из `parts` (source of truth
   по ролям — `mode_roles` в БД), НЕ из прозы в хвосте `work`: тот хвост дрейфует и врёт
   про роли. Для каждой части — key, scope, current_version (нужна как `base_version`),
   роли по режимам (mandatory / default_on / default_off). Прочитай тексты релевантных
   частей (`current-part`), не только work/interview. Карту покажи оператору ДО предложения
   патчей — страховка от «по умолчанию ушёл в work/interview».

2. **Рефлексия по прошлым правкам — ВСЕГДА перед поиском нового.** `patches --status applied`
   + при нужде `get-patch <id>`: какие правила оператор принял и когда. Прочитай несколько
   свежих диалогов (после applied_at) — прижилось правило (оператор перестал повторять
   поправку) или нет (повторяет → формулировка не считывается). Доложи компактно «прижилось /
   не прижилось и почему».
   - **Eviction / demote — рефлексия не только аддитивная.** Помимо «прижилось / не прижилось»
     для каждого applied-правила взвесь ход на УБОРКУ и предложи его наравне с добавлением.
     Основание — что правило стало вредить или потеряло смысл, а НЕ «модель научилась»: между
     сессиями модель ничего не запоминает, без инжекта правила поведения тоже не будет, поэтому
     «агент и так делает» — не аргумент за удаление. Реальные основания:
     * правило устарело после нового ADR / смены контура — больше не применимо;
     * правило избыточно — то же уже покрыто другой частью;
     * правило даёт негативный эффект — срабатывает не в том контексте, конфликтует с соседним,
       оператор в свежих диалогах спорит с ним / просит обратного.
     → предложи **ретайр** (`operation=delete`), если правило мёртвое/вредное целиком, либо
     **демоут роли** (`operation=set_roles`, `default_on`→`default_off`), если оно ещё
     ситуативно полезно, но не должно есть бюджет ядра по умолчанию. Доложи как находку,
     оформи `set_roles`/`delete`-патчем (шаг 9).
   - Самозагрязнение поиска: текст инструкции инжектится в диалог, поэтому grep по ключевику
     даёт ложный рецидив (часть `commit` буквально содержит свои примеры). При проверке
     рецидива ИСКЛЮЧАЙ совпадения, которые и есть инжектнутый текст части; смотри реальные
     tool-вызовы агента и реплики оператора, а не инжект.

3. **Vendor и период для нового разбора** уточни у оператора. Список vendor — СТРОГО из
   `sources`, не предлагай отсутствующих. Период парси из естественного вида сам.

4. **Найди и прочитай диалоги локально** (Read/Glob по путям из `sources`, фильтр по mtime/
   timestamp). Исключи conversation-id из `processed_conversation_ids` недавних сессий.
   - Объём: при сотнях диалогов сырьём не прочитать. Извлекай операторские реплики в дайджест
     и делегируй тяжёлое чтение саб-агентам, возвращая только цитаты-цеплялки (≤3 строки) —
     совпадает с privacy-инвариантом и общим work-правилом про саб-агентов. Сначала проходись
     компактно, глубоко читай только содержательное.

5. **Что ищем — операторские сигналы:** правила, которые оператор повторяет/формулирует
   («всегда X», «не делай Y», «предпочитай Z», «сначала спроси W»); корректирующие реплики;
   паттерны, закреплённые после нескольких итераций. Не сигнал: разовые баги, узкие
   технические решения, эмоции.

6. **Для КАЖДОГО сигнала сначала выбери НОСИТЕЛЬ, потом формулируй правку.** Развилка:
   - `user:work` / `user:interview` — кросс-проектное правило исполнения / прояснения постановки;
   - существующая спец-часть (`commit`, `tests`, `dotnet`, `contracts`, `mongo`, `postgres`,
     `frontend`, …) — правило про конкретный стек/контур; не тащи в ядро;
   - новая optional-часть под `free`-режим — правило, подключаемое по требованию (пример:
     research-gate). Создаёшь патчем `operation=create`, `base_version=0`, с явными
     `mode_roles` (текст + роли в одном патче, ADR-0038). НЕ полагайся на старый text-only
     путь: lazy-create без манифестных ролей оставлял новую часть с пустыми ролями и
     недоступной в композиции — поэтому роли задаёшь сам в патче;
   - ADR / проектная документация — сигнал Throne-specific или для одного репозитория (пример:
     codex parity). Здесь dream НЕ патчит — говорит «этому место в ADR проекта»;
   - no-op — уже покрыто существующей частью либо разовый случай.

7. **Перед добавлением — короткая проверка на дубль.** Нет ли этого правила уже в ядре или
   модульной части; не повторяется ли оно в нескольких. Если да — не добавляй, а схлопни/
   сошлись на существующую часть. Полный структурный разбор набора (разрастание ядра, мёртвые
   части, слияние близких) делается отдельным режимом — см. «Структурный аудит»; не вшивай его
   в каждый сигнальный проход.

8. **Обсуди находки интерактивно:** каждую — 1-2 строками: цитата-цеплялка (≤3 строки) +
   выбранный носитель. Согласуй формулировки и носители.

9. **Сформулируй патчи** через `propose-patch < payload.json`. Общие поля:
   - `target_scope` — всегда `"user"`; `target_key` — ключ носителя (любая user-часть; для
     новой optional-части — её новый ключ). system-части не патчи;
   - `base_version` — current_version носителя из карты (шаг 1); для НОВОЙ части — 0;
   - `rationale` — 1-3 предложения, ≤500 символов;
   - `idempotency_key` — ОБЯЗАТЕЛЬНО уникальный на каждый логический патч (≤64), напр.
     `dream-{vendor}-{date_to}-{target_key}-{seq}`. Без него повтор HTTP создаст дубль в /improvements.

   `operation` (default `replace_text`) выбирает форму правки — поля по операциям:
   - `replace_text` — `patch_text` = полное новое содержимое части целиком (сервер не мёржит);
   - `create` — новая часть: `patch_text` (текст) + `mode_roles` (роли), `base_version=0`;
   - `set_roles` — сменить роли существующей части: `mode_roles` = ПОЛНЫЙ желаемый набор
     (сервер заменяет, а не мёржит — текущий набор бери из `parts --json`, флипни нужный режим);
     `patch_text` можно опустить;
   - `delete` — ретайр части: ни `patch_text`, ни `mode_roles` не нужны.

   `mode_roles[] = {mode, role, order}`: `mode ∈ interview|work|review|dream|free`;
   `role ∈ mandatory|default_on|default_off`; `order` — позиция в композиции режима (целое ≥0).
   Демоут = тот же набор, но у одного режима `default_on`→`default_off`. Декомпозиция монолита =
   ПАРА патчей: `replace_text` урезает донора + `create` выносит вынутое в новую часть с ролями.

10. **В конце ОБЯЗАТЕЛЬНО** `record-session < session.json` — ОТДЕЛЬНАЯ session на КАЖДЫЙ
    разобранный vendor (frontier пер-vendor): `vendor`, `date_from`/`date_to`, `host`
    (hostname текущей машины — по нему сервер отделяет frontier разных машин), `summary`,
    `reflection` (оценка applied-патчей из шага 2), `processed_conversation_ids` (что реально
    прочитал — иначе следующий проход пересмотрит впустую), `proposed_patch_ids`. Даже если
    ничего не нашёл — запиши session с пустым `proposed_patch_ids` и `processed_conversation_ids`.

## Структурный аудит набора частей (standalone-режим)

Отдельный режим, НЕ привязанный к новому сигналу. Запускай его, когда:
- сигнальный проход (шаги 3–8) не нашёл ни одного нового операторского сигнала — вместо «ноль
  находок» осмысли НАБОР как граф; ИЛИ
- оператор явно просит аудит частей.

Шаги 1–2 (карта + рефлексия с eviction) остаются обязательными и здесь — аудит идёт ПОВЕРХ них.
Дальше пройдись по ВСЕМ user-частям (тексты через `current-part`, роли через `parts --json`) и
ищи три класса проблем:

1. **Разрастание ядра** — стек-/контур-специфика осела в `work`/`interview` (mandatory-ядро):
   правила про конкретный стек, тулинг, форж. → вынести в существующую или новую спец-часть.
2. **Дубли и пересечения** — одно правило живёт в нескольких частях или повторяет соседнюю
   формулировку. → схлопнуть в одну часть, на остальных убрать/сослаться; близкие по смыслу
   мелкие части — слить.
3. **Мёртвые / неиспользуемые части** — роль `default_off` нигде не включается, тема покрыта
   ADR/другой частью, правило устарело после смены контура. → ретайр или демоут.

Выход аудита — обычные патчи в `/improvements` (шаг 9), та же палитра операций:
- вынести из ядра / расщепить: `replace_text` урезает донора + `create`(+`mode_roles`) создаёт
  спец-часть с вынутым текстом;
- слить близкие: `replace_text` объединяющей части + `delete` поглощённой;
- понизить роль разросшегося правила: `set_roles` (`default_on`→`default_off`);
- выпилить мёртвую: `delete`.

Каждую находку сначала проговори оператору 1-2 строками (что и куда двигаем, почему), как в
шаге 8 — патчи формулируй после согласования. Финал — `record-session` (шаг 10) с
`summary`, описывающим аудит, даже если патчей ноль. Поле `vendor` обязательно и валидируется
по `sources`: для аудита, начатого из пустого сигнального прохода, бери тот же vendor; для
аудита по явной просьбе без разбора диалогов — vendor из `sources` (уточни у оператора, если
их несколько), с пустым `processed_conversation_ids`.

## Жёсткие инварианты

- Карту частей показывай ДО патчей; рефлексию делай ВСЕГДА перед поиском нового.
- Не применяй патчи сам — apply/edit/reject исключительно user-action в UI `/improvements`.
- Не патчи `system`-части: они manifest-managed (`specs/manifest/throne-system-prompt-parts.yaml`), меняются
  только PR к манифесту, вне объёма dream.
- dream сам не пишет код и не правит ADR — но вправе РЕКОМЕНДОВАТЬ носителем сигнала ADR.
- Не предлагай rule с toxic absolutism («никогда», «всегда без исключений»), если есть
  смысловые исключения.
- Не намекай на vendor, которого нет в `sources`. Не публикуй в чат сырые тексты чужих
  диалогов — только цитаты-цеплялки (≤3 строки). Не превышай заказанный объём.
